# 发布流程

本文面向发布维护者，说明版本发布、分发和自动更新的基本原理。应用版本以版本清单、tag 和 GitHub Release 为准。

## 发布准备

从最新 main 创建发布准备分支，统一应用版本、兼容说明和 CHANGELOG。版本清单与 tag 必须一致；缩略图提供程序保持独立版本。准备阶段标记为“待发布”，合并审查通过的 PR，并等待 main 的 CI 成功后再创建 tag。

发布使用受保护的 release Environment，密钥和证书由环境管理。正式项目密钥必须沿用原值，名称迁移不能改变密钥内容，详见[项目文件契约](../src-tauri/src/project_file/README.md)。

发布前完成代码、安装器、资源许可证和项目兼容性检查。README 保持产品介绍，用户指南记录操作方法，CHANGELOG 记录版本变化。真实模型、GPU 和媒体编码验证单独执行，不进入普通 CI。

本地完整构建使用 `npm run release:build -- <版本>`。它会同步版本并生成发布附件，适用于构建发布包；仅修改文档时无需运行。

## 构建与发布

发布工作流遵循“校验 → 双平台构建 → 创建草稿”的顺序。

校验阶段确认 tag 对应的提交已通过 main 的 CI。构建固定使用该提交，上传前再次确认 tag 未移动。手动重跑可以使用 main 上的工作流，但应用源码仍取自指定 tag。

Windows 与 macOS 分别构建安装包和更新包。构建任务只有读取权限，独立的发布任务负责核对附件并写入 Release。模型与媒体工具使用固定资源和摘要，缓存复用时仍须校验。

发布任务重新计算附件摘要，生成清单后创建或复用草稿。附件上传完成并复核后，由维护者检查发布说明和兼容提示，再公开发布。只有比当前正式版更新的正式版本设为 latest；preview 保留 prerelease 标记。

预发布生成安装附件，但不生成 `latest.json`，也不进入正式更新目录。正式发布后更新 CHANGELOG 的状态，已有 tag 保持不变。

## 发布清单与分发

正式版附件包含完整安装包、专用更新包、`latest.json` 和 `SHA256SUMS.txt`。清单按 Windows x64 与 macOS arm64 区分平台，分别记录完整包和更新包的地址与摘要。

`signature` 表示文件实际的 SHA-256 摘要，用于验证内容一致性。`pub_date` 记录附件生成时间，不参与版本新旧比较。完整包用于安装和修复，更新包用于升级已有安装。

OpenList 将最新正式 Release 的附件同步到 CDN。安装包和更新包应先就绪，再更新清单，避免客户端发现版本后找不到对应文件。桌面端以 CDN 当前清单为准，因此发布完成还需确认同步结果。

官网与桌面端使用不同的下载策略。官网优先读取 CDN，保留 GitHub 回退；下载入口确认安装包可用后让浏览器直接下载。桌面自动更新只使用 CDN，不使用官网的回退机制。官网和文档站由各自工作流部署。

## 桌面自动更新

正式版和 preview 构建共用 CDN 更新源，只接收更高版本号的正式版。比较遵循 SemVer：同一基础版本的正式版高于 preview，例如 `0.4.3-preview` 可以更新至 `0.4.3`；`0.4.4-preview` 不会降至 `0.4.3`。

版本发现、更新包下载、版本说明和安装前校验全部来自 CDN，不请求 GitHub 作为回退源。说明取自清单的 `notes`，缺省时为空。CDN 请求失败时，手动检查显示错误，启动后台检查保持静默。

客户端下载更新包后校验文件头与 SHA-256，再提示安装。安装前重新读取 CDN 清单，确认版本和摘要一致，并复验本地文件。若 CDN 已切换到新版本，需重新检查更新。该机制依赖 CDN 内容可信与 HTTPS，摘要用于完整性校验，不是离线签名。

自动安装不可用时，保留用户主动打开发布页的手动下载入口。已下载更新和忽略状态会持久化；忽略只影响该版本的自动提示，不影响手动检查和后续版本。

## 安装与恢复

更新包携带应用文件，复用已安装的大型模型、媒体工具和推理依赖。复用前按目标版本的清单检查内容，依赖缺失或不匹配时使用完整安装包修复。

开始更新前，应用等待写入完成并按需保存项目。Windows 更新器确认接管后关闭应用，再执行安装；macOS 在临时目录组装并验证应用包，再替换原应用。更新完成后重新打开软件和已保存项目。

安装以可恢复的文件替换为原则：修改前保留旧文件，校验通过后提交，失败时恢复。取消安装也需完成必要的恢复操作。恢复未完成时保留备份，避免覆盖可恢复的数据。

安装器只管理已识别的应用文件，用户项目和数据不属于更新清理范围。完整安装、修复和更新共用资源校验原则；自动更新继承已有组件选择。

## 失败处理

失败发生在哪个阶段，就重跑相应阶段。仅发布草稿失败时复用已有构建产物；构建失败或产物过期时重新构建。已上传且摘要一致的附件可以复用。

已公开的 tag 不移动。需要修改应用源码时发布新版本，避免同一版本对应不同产物。发布完成后核对 GitHub 附件、CDN 同步和官网下载入口；本地构建成功不代表公开分发已经完成。
